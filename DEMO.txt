1. MENTAL MODEL: WHAT HERALD DOES
=================================

The simplest way to explain Herald:

"Herald takes suspicious domains and URLs, enriches them with security context, scores them with ML and rules, builds an investigation timeline with evidence, and gives the analyst a defensible verdict instead of another raw alert."

The full data flow:

1. Ingestion
------------

Herald starts with candidate security signals. In a mature SOC deployment, those can come from:
- Certificate Transparency feeds.
- Newly registered domain feeds.
- Internal reports from analysts.
- API submissions from SIEM/SOAR workflows.
- Mock/demo attack scenarios in the frontend.
- Future integrations with EDR, proxy logs, email gateways, or DNS logs.

For this repo, the strongest implemented path is suspicious-domain and phishing-domain intake. The API can queue a scan or investigation. The CLI can run a direct investigation. The ingestion layer is where raw input gets normalized: "URL or domain in, clean domain object out."

Say this to a CISO:
"The platform is source-agnostic. The current strongest use case is phishing/lookalike-domain intelligence, but the architecture is built around the same pattern a SOC already uses: ingest signal, normalize it, score it, enrich it, and turn it into an analyst-ready case."

Concrete example:
Input:
  https://hdfc-netbanking-verify.top/login

Normalized target:
  domain = hdfc-netbanking-verify.top
  source = api_investigate
  trace_id = trc-demo-001
  lifecycle_state = QUEUED

2. Safety and normalization
---------------------------

Before Herald fetches or screenshots a target, it must protect itself. A suspicious URL is untrusted input. It might point to localhost, cloud metadata endpoints, private IP ranges, or malformed URLs.

The safety layer validates:
- URL scheme.
- Hostname.
- Private or loopback IP behavior.
- Whether private targets are allowed for testing.

What to say:
"Because Herald can fetch pages and run browser analysis, SSRF protection is a core control. We do not treat submitted URLs as harmless strings. The platform validates targets before enrichment."

3. Feature engineering
----------------------

The features layer converts raw strings and observations into measurable risk signals.

For phishing/lookalike domains, Herald extracts signals like:
- Domain length.
- Number of hyphens.
- Digit ratio.
- Suspicious TLDs such as .xyz, .top, .click.
- Brand keywords such as SBI, HDFC, ICICI, UIDAI, IRCTC, NIC.
- Whether the brand appears in the registered domain or only in a subdomain.
- Fuzzy similarity to protected brands.
- Punycode/homoglyph indicators.
- Suspicious words: login, verify, secure, update, account, banking.
- DNS records.
- TLS certificate metadata.
- WHOIS/domain age.
- Page content signals such as password fields or external form actions.
- Visual/OCR evidence from screenshots.

What to say:
"The model is not guessing from a black-box screenshot. It sees structured features that security teams already understand: brand impersonation, domain age, suspicious TLDs, certificate behavior, login forms, and visual credential-harvesting cues."

4. ML scoring
-------------

Herald's ML model turns the feature vector into a confidence score. The current code uses an ensemble-style approach, combining tree-based model outputs such as Random Forest and gradient boosting/XGBoost-style scoring. The score is then mapped to operational states:
- Clean: low-risk.
- Suspected: needs more enrichment or analyst review.
- Phishing: high-confidence malicious/suspicious verdict.
- Rejected/Failed/Degraded: operational states when safety checks or dependencies fail.

Important framing:
"The ML model does not replace analyst judgment. It reduces the candidate set and prioritizes the highest-risk cases. Borderline cases are where Herald deliberately adds more evidence instead of forcing a premature binary decision."

5. Enrichment and investigation
-------------------------------

Once a domain is suspicious or borderline, Herald enriches it:
- DNS intelligence.
- WHOIS/domain age.
- TLS certificate details.
- Content inspection.
- Browser screenshot.
- OCR text extraction.
- Risk factor generation.
- Stage-by-stage timeline.

This becomes an investigation record, not just an alert.

What to say:
"The analyst does not just see 'ML says phishing.' They see why: new domain, suspicious TLD, HDFC keyword, verify/login wording, password form, external submission, screenshot, and OCR text."

6. Analyst action
-----------------

The analyst can:
- Review the verdict and score.
- Inspect evidence.
- Export JSON/PDF reports.
- Mark true positive or false positive.
- Add legitimate domains to whitelist.
- Escalate to takedown, blocking, user notification, or SIEM/SOAR playbook.
- Feed analyst decisions back into model-quality tracking.

What to say:
"Herald's output is designed to be operational. A detection is only useful if it helps the analyst decide what to do next."

7. Operations and feedback loop
-------------------------------

The monitoring and telemetry layers show:
- Queue depth.
- Worker health.
- Visual-analysis backlog.
- Circuit breaker state.
- Dead-letter queue.
- API readiness.
- Redis/Postgres health.
- Trace spans.

What to say:
"A CISO should not only ask whether the model works. They should ask whether the detection service is healthy, observable, and recoverable. Herald exposes queue depth, worker liveness, degraded states, and failed-job paths so operators can trust the pipeline."


2. 20 CISO-LEVEL QUESTIONS AND ANSWERS
======================================

1. "What problem does Herald solve that my SIEM does not already solve?"

Answer:
"Your SIEM is excellent at collecting and correlating broad telemetry, but it often leaves analysts with raw alerts and manual enrichment work. Herald focuses on one high-volume, high-impact workflow: suspicious and lookalike domain investigation. It takes a candidate domain, enriches it, scores it, captures evidence, explains the risk factors, and produces an analyst-ready case. I would position Herald as a detection and investigation layer that can feed the SIEM, not as a SIEM replacement."

2. "How does Herald reduce false positives?"

Answer:
"It reduces false positives in three ways. First, it uses multiple signal families rather than a single rule: lexical features, DNS, WHOIS, TLS, content, and visual/OCR evidence. Second, it has a 'Suspected' state for borderline cases instead of forcing everything into malicious or benign. Third, analyst feedback and whitelisting can close the loop so known legitimate domains stop consuming analyst time. The key point is that the model score is not the only decision; the evidence bundle helps validate or reject the alert."

3. "What is your measured false positive rate?"

Answer:
"For a production CISO review, I would bring a benchmark table rather than rely on a single number. The metric I would show is precision, false-positive rate on known legitimate domains, and false-negative rate on recent phishing feeds. The README currently cites high precision on live PhishTank-style validation, but before a buying or board-level conversation I would rerun the benchmark on the latest holdout set and show date, sample size, source, and confidence intervals. My honest answer is: Herald is designed to measure and reduce false positives, and I would validate the rate against your environment before operational rollout."

4. "Can we audit why a domain was classified as phishing?"

Answer:
"Yes. Herald is built around explainability. The analyst can see the features and evidence behind the verdict: suspicious TLD, brand keyword placement, fuzzy brand match, domain age, certificate metadata, login form detection, external form action, screenshot, OCR text, and stage timeline. The output can be exported as JSON or PDF, which makes it usable for incident review, takedown requests, and audit trails."

5. "Where does our data go?"

Answer:
"Herald is designed to be self-hosted. The detection pipeline, models, database, queues, and evidence artifacts can run inside your infrastructure. That means domain watchlists, screenshots, OCR text, and investigation records do not need to leave your environment. This is especially important for regulated sectors where screenshots or investigation artifacts may contain sensitive internal context."

6. "Does Herald require VirusTotal, Shodan, or paid threat-intel feeds?"

Answer:
"No, the core design does not require paid third-party APIs. Herald can use local ML, DNS/TLS/WHOIS enrichment, browser analysis, and internal feeds. It can integrate external intelligence later, but the base value proposition is local, self-hosted, evidence-driven detection."

7. "How does the ML model work in plain English?"

Answer:
"The model looks at traits that phishing domains tend to have: impersonated brand names, suspicious TLDs, unusual spelling, login or verification words, fresh domain age, certificate behavior, and page-content signals. It converts those traits into a feature vector and produces a risk score. High-confidence cases can be flagged quickly; borderline cases get more evidence through content and visual analysis."

8. "What does PS-02 mean and why should I trust that dataset?"

Answer:
"PS-02 appears to be a labelled phishing-detection problem-statement dataset, likely from a structured cybersecurity challenge or evaluation track. In Herald, it is used as labelled training and shortlisting data, supplemented by mock data and external phishing/legitimate sources. I would not ask a CISO to trust the name alone. I would show dataset provenance, label definitions, class balance, train/test split methodology, and performance on a recent holdout set."

9. "How does Herald integrate with our existing SOC stack?"

Answer:
"The practical integration path is API-first. A SIEM, SOAR, EDR workflow, email gateway, DNS platform, or proxy can submit a domain to Herald through the API. Herald returns a verdict and evidence that can be pushed back into the SIEM or used to trigger SOAR playbooks. The dashboard is useful for demonstration and operations, but the long-term enterprise path is API plus webhook/SOAR integration."

10. "Can it map detections to MITRE ATT&CK?"

Answer:
"For phishing-domain workflows, the closest ATT&CK alignment is initial access via phishing and supporting infrastructure techniques such as domain registration, masquerading, and credential harvesting behaviors. I would present MITRE mapping as a coverage layer: Herald detects phishing infrastructure and credential-harvesting indicators, then maps those findings to ATT&CK tactics such as Initial Access and Credential Access. I would not claim full ATT&CK coverage across endpoint, lateral movement, or exfiltration unless those telemetry sources are integrated."

11. "What is the analyst efficiency gain?"

Answer:
"The efficiency gain comes from removing manual enrichment. Instead of asking an analyst to check WHOIS, DNS, TLS, page content, screenshots, and brand similarity by hand, Herald packages that into one workflow. The KPI I would show is time-to-triage per domain: manual process versus Herald-assisted process. For the demo, I would show that a suspicious domain can move from submission to enriched evidence in minutes or seconds depending on visual analysis."

12. "How does it handle model uncertainty?"

Answer:
"It does not hide uncertainty. Herald uses an intermediate 'Suspected' state for borderline cases. Those cases can trigger additional enrichment such as content inspection and screenshot/OCR. That is the right operational behavior: do not overclaim, gather more evidence, and preserve analyst review for ambiguous cases."

13. "What happens if DNS, WHOIS, Redis, or the browser worker fails?"

Answer:
"Herald is designed to degrade rather than silently fail. Investigation stages can be marked degraded, Redis queues have ready/processing/delayed/DLQ states, and visual analysis has timeout and circuit-breaker controls. The operator can see queue depth, worker health, browser pressure, and failed jobs. A failed screenshot should not erase the lexical and DNS evidence already collected."

14. "How do you prevent Herald from becoming an SSRF tool?"

Answer:
"Submitted URLs are treated as hostile. Herald validates targets before fetching or screenshotting them, with controls around URL scheme, hostname, and private-network access. Private targets should only be allowed explicitly for controlled testing. Browser analysis is isolated and timeout-bound."

15. "What is the ROI?"

Answer:
"ROI comes from earlier detection, fewer manual enrichment steps, and reduced analyst time spent on low-quality alerts. A simple ROI model is: number of suspicious-domain alerts per month multiplied by manual triage minutes saved, plus reduced risk from earlier takedown/blocking. Against IBM's breach-cost backdrop, where average breach costs remain in the multi-million-dollar range and breach lifecycles are still measured in hundreds of days, even modest reductions in time-to-detect and time-to-triage are material."

16. "Can we deploy it on-premises?"

Answer:
"Yes. The architecture is self-hostable: Python backend, database, Redis queues, model artifacts, workers, and Next.js frontend can run inside controlled infrastructure. That is one of the core design choices: data residency and operational control."

17. "How do you update or retrain the model?"

Answer:
"The research layer keeps raw, processed, and external datasets separate. The retraining workflow builds datasets, extracts features, trains a model version, evaluates it against holdout and external data, and promotes the artifact into the models directory. The critical control is feature parity: the same production feature extractors used at inference must match the training feature set."

18. "What are the main security risks of Herald itself?"

Answer:
"The big ones are untrusted URL handling, sensitive evidence storage, model poisoning, and access control. The mitigations are SSRF controls, restricted artifact access, model provenance, audit logging, role-based permissions, and retention policies for screenshots/OCR."

19. "What does the dashboard show that matters to me?"

Answer:
"For a CISO, the dashboard should show operational trust: detection volume, suspicious and malicious verdicts, confidence distribution, queue backlog, degraded dependencies, dead-letter jobs, and analyst feedback trends. It answers: are we detecting, are analysts overloaded, and is the platform healthy?"

20. "What should I not use Herald for today?"

Answer:
"I would not position Herald today as a complete SIEM, complete EDR, or full ATT&CK coverage platform. Its strongest current use case is phishing/lookalike-domain detection and evidence-driven investigation. It can integrate with broader SOC tooling, but it should not replace those systems."

-----------------------------------------------------

"Who labelled this data? How do I know it reflects our threat landscape?"

6. HOW TO FRAME THE ML MODEL
============================

Bad explanation:
"We trained a classifier using PS-02 data and it predicts phishing."

Better explanation:
"Herald learns the patterns of phishing infrastructure. It looks at domains the way an experienced analyst would: is a protected brand being impersonated, is the TLD risky, is the domain newly created, does the certificate look fresh, is there a login form, does the page ask for credentials, and does the screenshot/OCR confirm the lure? The model turns those signals into a risk score, and the investigation pipeline turns the score into evidence."

Plain-language model story:

1. What threats does it detect?
-------------------------------

"It detects suspicious and phishing domains, especially lookalike domains that impersonate banks, government portals, telecom providers, and public-service brands. The strongest use case is early detection of credential-harvesting infrastructure."

2. What is PS-02?
-----------------

"PS-02 is the labelled problem-statement dataset used as a foundation for training and validation. It contains training examples and shortlisting/evaluation data. In plain English, it gives the model examples of domains and evidence that are phishing-like versus legitimate."

Say carefully:
"PS-02 is not magic. It is labelled evidence. The model is only as trustworthy as the labels, split strategy, and validation data. That is why I would show separate performance on fresh external feeds and customer-specific legitimate domains."

3. What features does the model use?
------------------------------------

Say:
"The model uses features that are understandable to a security team."

Examples:
- Brand keyword in domain: HDFC, SBI, ICICI, UIDAI, IRCTC.
- Suspicious action words: login, verify, secure, update, banking.
- Suspicious TLD: .xyz, .top, .click.
- Fuzzy typo distance to known brands.
- Domain length and hyphen patterns.
- Punycode/homoglyph indicators.
- DNS and MX/SPF posture.
- TLS certificate presence, issuer, age, and domain match.
- WHOIS/domain age.
- Page content: login forms, password fields, external form action.
- OCR text: visible credential-harvesting language.

4. How accurate is it?
----------------------

Say:
"The right way to discuss accuracy is not one number. I would show precision, recall, false-positive rate, false-negative rate, and performance by data source. Precision tells us how much analyst time we waste. Recall tells us how much phishing we miss. For a CISO, those two numbers matter more than generic accuracy because phishing datasets are imbalanced."

Memorisable answer:
"I care about precision because false positives burn analyst time, and I care about recall because false negatives become incidents. Herald is designed to tune that tradeoff and use a 'Suspected' state for uncertainty."

5. Can it be audited?
---------------------

Say:
"Yes. The model output is tied to evidence. A reviewer can see which features and investigation stages supported the score. The pipeline can export JSON/PDF evidence, and model versions should be tied to dataset versions, feature lists, thresholds, and evaluation results."

6. What happens when the model is uncertain?
--------------------------------------------

Say:
"Uncertainty is not hidden. Low-risk domains can be marked clean, high-risk domains can be flagged quickly, and borderline domains are marked suspected and enriched further with content and visual analysis."

7. What should you avoid saying?
--------------------------------

Avoid:
- "The AI detects phishing automatically."
- "The model is fully accurate."
- "This replaces analysts."
- "This covers all MITRE ATT&CK."
- "The dataset proves real-world performance forever."

Say instead:
- "The model prioritizes and explains suspicious domains."
- "The analyst gets evidence, not just a score."
- "We validate against current data and tune thresholds."
- "This integrates with the SOC stack."
- "The system is designed for measurable reduction in triage time and false positives."


FINAL MEMORISABLE POSITIONING
=============================

"Herald is a self-hosted, evidence-driven phishing-domain investigation platform. It ingests suspicious domains, extracts auditable risk signals, scores them with ML and rules, enriches borderline cases with DNS/TLS/content/visual evidence, and gives the analyst a defensible verdict and next action. The CISO value is lower triage time, better explainability, local data residency, and a measurable path to reducing false-positive burden."
