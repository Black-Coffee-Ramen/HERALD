\section{Executive Summary}
HERALD is a self-hosted phishing-domain detection, investigation, and operations platform. The current implementation combines a Python CLI, FastAPI backend, Redis-backed workers, SQLAlchemy persistence, browser/OCR evidence capture, telemetry, and a Next.js operations console. The active platform model is \texttt{models/ensemble\_v7.joblib}; newer v8/v9 artifacts are research outputs unless explicitly configured.

\section{Problem Statement}
HERALD targets phishing and typosquatting domains aimed at Critical Sector Entities, especially Indian banking, government, telecom, and public-service brands. It avoids reliance on commercial external threat-intelligence APIs and emphasizes on-premises evidence generation.

\section{Execution Flow}
\subsection{CLI}
The console script \texttt{herald=herald.cli:main} invokes \texttt{InvestigationPipeline}. The pipeline normalizes targets, validates SSRF safety, extracts lexical features, collects DNS/WHOIS/TLS intelligence, optionally captures screenshots and OCR via Playwright/Tesseract, combines scores, and writes evidence under \texttt{evidence/trc-*}.

\subsection{API and Workers}
FastAPI queues jobs to Redis. The domain worker loads \texttt{PhishingPredictorV3}, uses the v7 ensemble, updates \texttt{DomainScan}, and optionally queues visual work. The visual worker runs Playwright analysis in a subprocess with timeout and circuit-breaker protection, then updates screenshot/OCR columns.

\section{Machine Learning}
The active predictor uses RandomForest and XGBoost probabilities combined as $0.4 RF + 0.6 XGB$. It extracts lexical, network, and WHOIS features, then applies content boosts for borderline domains. v8/v9 are later experiments but not active in default runtime.

\section{Deployment}
The top-level \texttt{docker-compose.yml} runs Redis, API, domain worker, and visual worker. It does not run PostgreSQL, Next.js, Streamlit, Certstream, or social monitors. SQLite is the default database unless \texttt{DATABASE\_URL} is set.

\section{Security}
The repository includes SSRF guards, JWT auth, bcrypt password hashing, non-root Docker user, and visual-worker isolation. Production gaps include permissive CORS, public registration, default JWT secret fallback, incomplete frontend auth, and trusted pickle model loading.

\section{Technical Debt}
The main reliability issue is in \texttt{RedisReliableQueue}: non-terminal retries are not re-enqueued, and immediate DLQ handling references an out-of-scope \texttt{attempts}. Other debt includes outdated docs, legacy Streamlit, inactive v9 runtime, missing migrations, and duplicated visual-analysis stacks.

\section{Conclusion}
HERALD has a strong technical core and a substantial research trail. The implementation should now be consolidated around the active CLI/API/worker/Next.js architecture, with queue reliability, model configuration, frontend auth, and deployment hardening as immediate priorities.
